# Техническое задание HotCached

[English](SPECIFICATION.md) | [Русская версия](SPECIFICATION.ru.md)

**Статус:** согласованная архитектура планируемого MVP. Пункты, отмеченные как требующие проверки, нельзя считать реализованными до испытаний.

## 1. Назначение и границы

HotCached — локальная Linux-служба рядом с TorrServer. Она поддерживает ограниченный набор torrent'ов в сессии libtorrent и заранее скачивает только pieces, покрывающие заданные диапазоны HEAD и TAIL выбранных медиафайлов. TorrServer по-прежнему отвечает за потоковое воспроизведение, буферизацию и перемотку; HotCached помогает тем, что выступает дополнительным BitTorrent-пиром с уже доступными полезными pieces.

Не входит в MVP: замена TorrServer, отслеживание позиции просмотра, обработка PlaybackProgress/PlaybackStop, предзагрузка произвольных точек перемотки, намеренное скачивание медиа целиком, наблюдение за каталогами STRM, зависимость от Tiramisu или изменение внутреннего кода TorrServer.

## 2. Компоненты и ответственность

- **Jellyfin:** отправляет вебхуки ItemAdded и PlaybackStart; API/source resolution используется для определения реально выбранного источника.
- **TorrServer:** независимый streaming engine. HotCached не добавляет и не удаляет torrent'ы через API TorrServer.
- **libtorrent 2.1.x:** одна BitTorrent-сессия, metadata, обнаружение пиров, приоритеты и проверка pieces, per-torrent bandwidth limits, resume data.
- **HotCached:** приём вебхуков, определение источника, политика кэширования, очереди, вытеснение, учёт, конфигурация и диагностика.
- **SQLite:** постоянное состояние приложения и очередей.
- **Единый каталог на SSD:** физическое хранилище. Очередь определяется записью в БД, а не именем каталога.

## 3. Обработка событий

### ItemAdded

1. Проверить webhook и получить сведения об элементе/источнике Jellyfin.
2. Надёжно установить, что источник — STRM, ведущий на настроенный TorrServer.
3. Извлечь infohash и индекс файла из поддерживаемого playback URL.
4. Если torrent ещё не отслеживается, добавить его в PREWARM после проверки лимитов.
5. Получить metadata, рассчитать нужные pieces и начать их загрузку.

Если принадлежность источника не подтверждена, событие игнорируется с записью причины в журнал. Нельзя определять torrent по названию фильма или каталогу медиатеки.

### PlaybackStart

1. Разрешить MediaSource, **фактически выбранный** для воспроизведения; использовать MediaSourceId, если он доступен.
2. Проверить, что источник ведёт на настроенный TorrServer.
3. Извлечь infohash и file_index.
4. Если torrent уже в ACTIVE, обновить только last_played_at.
5. Если он в PREWARM, перевести существующую запись/handle в ACTIVE без создания дубликата.
6. Иначе добавить torrent напрямую в ACTIVE.
7. При необходимости вытеснить старые записи и пересчитать bandwidth.

PlaybackProgress и PlaybackStop в MVP игнорируются.

**Требует проверки:** точный вызов Jellyfin API для разрешения выбранного MediaSource нужно подтвердить на установленной версии Jellyfin. Если источник неоднозначен или недоступен, безопасное поведение — проигнорировать событие.

## 4. Проверка источника и разбор URL

В конфигурации задаётся канонический базовый URL TorrServer, например `http://192.168.0.14:8097`. Нормализовать схему, hostname и порт и сравнивать origin URL источника. Дополнительно проверять ожидаемый путь воспроизведения TorrServer; не принимать любой URL только потому, что совпал хост.

Для подтверждённого URL вида `/play/{hash}/{id}` извлечь:
- `infohash`: нормализованный lowercase hexadecimal infohash с проверкой формата/длины;
- `file_index`: неотрицательный целочисленный индекс файла torrent'а.

Игнорировать чужие host/port, неподдерживаемые пути, неверные hash/index и обычные локальные файлы. Query string не должен ломать разбор.

Для PlaybackStart предпочтителен реально выбранный MediaSource, а не путь элемента медиатеки по умолчанию. Для ItemAdded выбранного источника воспроизведения нет, поэтому нужен проверенный запрос к Jellyfin API или чтение содержимого STRM, если путь доступен. Если ни один способ не подтверждает URL, PREWARM не создаётся.

## 5. Политика очередей

| Параметр | ACTIVE | PREWARM |
|---|---:|---:|
| max_items | 20 | 20 |
| max_cache_bytes | 5 GiB | 5 GiB |
| download_bandwidth | 15 Mbit/s | 5 Mbit/s |

Общий предел загрузки HotCached — 20 Mbit/s.

Полоса делится поровну между torrent'ами одной очереди и пересчитывается при изменении состава. Неиспользуемая полоса между очередями в MVP не передаётся. Помимо per-torrent limits, задать session-wide cap как дополнительный предохранитель. Единицы и точное поведение проверить на выбранной сборке libtorrent.

Все torrent'ы управляются приложением явно: `auto_managed = false`. Auto-management libtorrent не должен решать, какие записи входят в очереди.

### Promotion и идемпотентность

- ItemAdded добавляет подходящий новый torrent в PREWARM, только если он ещё не отслеживается.
- Повторный ItemAdded не создаёт дубликат и не обновляет возраст существующей записи.
- PlaybackStart для PREWARM переводит существующую запись/handle в ACTIVE.
- PlaybackStart для ACTIVE обновляет last_played_at.
- PlaybackStart для неизвестного torrent добавляет его в ACTIVE.
- Последний реальный просмотр важнее времени добавления в медиатеку.

## 6. Лимиты и вытеснение

Каждая очередь независимо соблюдает лимит количества элементов и объёма кэшированных payload bytes. Перед добавлением вычислить набор нужных pieces и оценить их полный объём с учётом пограничных pieces. Если запись не помещается, вытеснять LRU-записи целевой очереди, пока не освободится место или очередь не опустеет. Если даже одна запись превышает лимит байтов, не добавлять её и записать понятную причину. Нельзя скачивать часть piece ради попадания в бюджет.

Для ACTIVE LRU определяется по last_played_at, при равенстве используется added_at. Для PREWARM — по added_at. Вытеснение реактивное: TTL и периодическая очистка в MVP не нужны.

Вытеснение удаляет handle libtorrent, принадлежащие HotCached файлы данных/resume и записи БД, но никогда не изменяет список torrent'ов, кэш или данные TorrServer.

## 7. Идентификация torrent и несколько файлов

На каждый уникальный infohash приходится один libtorrent handle и одно физическое torrent-хранилище. Лимиты очередей считаются по уникальным infohash, а не по STRM-элементам.

У torrent может быть несколько media targets с разными file_index. Для каждого target вычисляются HEAD/TAIL pieces; итоговый набор torrent'а — объединение множеств. Общие pieces учитываются один раз. PlaybackStart другого файла того же torrent обновляет актуальность и добавляет необходимые pieces без создания второго handle.

Рекомендуемая модель БД:
- `torrents`: одна запись на infohash, очередь, added_at, last_played_at, cached_bytes, metadata/resume state и диагностика;
- `media_targets`: запись на пару (infohash, file_index), размер файла, piece length и данные target.

Согласованные минимальные поля (infohash, file_index, queue, added_at, last_played_at, cached_bytes) должны быть представлены. В нормализованной схеме file_index относится к media_targets, остальные поля очереди — к torrents.

## 8. Выбор pieces

Значения по умолчанию:
- `head_bytes = 64 MiB`
- `tail_bytes = 16 MiB`
- `piece_priority = 1`

Для размера файла S:
- HEAD: [0, min(head_bytes, S))
- TAIL: [max(0, S - tail_bytes), S)

Диапазоны преобразуются через API libtorrent для сопоставления файла и pieces. Создаётся множество уникальных номеров. После получения metadata всем pieces назначается priority 0, нужным — priority 1. При восстановлении и добавлении нового target приоритеты применяются повторно.

Piece неделима: если она пересекает нужный диапазон, скачивается целиком. Для маленького файла пересечение диапазонов не создаёт дубликатов. В MVP не вводить отдельные размеры для 1080p/4K, bitrate или масштабирование по размеру файла.

В multi-file torrent одна piece может пересекать границы файлов. Если piece нужна одному target, её payload может содержать байты соседнего файла; учитывается фактическая стоимость всей piece.

## 9. Учёт и хранение кэша

`cached_bytes` — сумма payload bytes уникальных нужных pieces, которые полностью загружены и проверены, без двойного счёта. Не заменять этот показатель видимым размером sparse-файла, полным размером медиафайла или номинальной суммой HEAD+TAIL.

Поддерживать состояние завершения pieces из libtorrent и сверять его при запуске. Незавершённые pieces не считаются кэшированными. Разделять:
- логический бюджет payload каждой очереди;
- фактически свободное место на файловой системе.

Предлагаемый предохранитель по умолчанию: `minimum_free_disk_bytes = 10 GiB`. Если после добавления будет нарушен резерв, отклонять PREWARM. Для ACTIVE сначала разрешается вытеснить существующие ACTIVE-записи, но резерв свободного места нарушать нельзя. Точное поведение проверить тестами.

Единый root, например `/mnt/hotcached`. Не создавать каталоги очередей. Допустимы технические подкаталоги по infohash. Promotion меняет только состояние в БД и не перемещает файлы.

## 10. Metadata и обнаружение пиров

URL даёт infohash и file_index, но не обязательно metadata torrent'а. Добавлять по infohash, затем получать metadata у доступных пиров. Настроить подходящие механизмы peer discovery (DHT/LSD/PEX — с учётом типа torrent'а и параметров libtorrent).

**Требует проверки:** metadata может быть недоступна для некоторых private torrent'ов. Нужно документировать поддерживаемые сценарии и корректно обрабатывать отсутствие metadata.

**Критический интеграционный тест:** доказать, что TorrServer подключается к HotCached для того же infohash и запрашивает закэшированные pieces. Проверить LAN discovery и поведение local peers. Если потребуется прямое соединение, сначала выяснить, как TorrServer сообщает свой BitTorrent listen endpoint. Нельзя считать, что работа на одном хосте гарантирует соединение.

HotCached не должен становиться неограниченным публичным seed. Проверить upload и доступ локальных пиров; ограничения внешней отдачи не должны мешать TorrServer получать pieces.

## 11. Сохранение состояния и рестарт

Изменения очередей и targets выполнять транзакционно в SQLite. Сохранять resume data libtorrent и достаточно metadata для восстановления.

При старте:
1. прочитать конфигурацию и БД;
2. проверить cache/resume файлы;
3. восстановить валидные handles;
4. сверить проверенные pieces и cached_bytes;
5. повторно применить piece priorities и bandwidth limits;
6. вытеснить старые записи, если новые лимиты конфигурации меньше прежних.

Отсутствующие или повреждённые resume data не должны обрушать сервис. Не удалять файлы вне каталога HotCached.

## 12. Конфигурация

Файл: `/etc/hotcached/config.toml`.

```toml
[jellyfin]
url = "http://127.0.0.1:8096"
api_token = "CHANGE_ME"

[webhook]
bind = "127.0.0.1"
port = 9120
path = "/webhook"
auth_token = "CHANGE_ME"

[torrserver]
url = "http://192.168.0.14:8097"

[cache]
path = "/mnt/hotcached"
head_bytes = "64MiB"
tail_bytes = "16MiB"
piece_priority = 1
minimum_free_disk_bytes = "10GiB"

[global]
download_bandwidth = "20Mbit/s"

[active]
max_items = 20
max_cache_bytes = "5GiB"
download_bandwidth = "15Mbit/s"

[prewarm]
max_items = 20
max_cache_bytes = "5GiB"
download_bandwidth = "5Mbit/s"
```

Токены являются секретами: файл должен читаться только root и сервисной учётной записью. Не записывать токены в журналы. Парсер проверяет значения, нормализует единицы, запрещает отрицательные лимиты и проверяет, что сумма полос очередей не превышает общий лимит.

## 13. Диагностика и служба

Предлагаемые локальные endpoints:
- `GET /health`: состояние процесса, БД и session;
- `GET /status`: количество элементов, байты и лимиты очередей;
- `GET /cache`: подробности по torrent и target.

Поля torrent: infohash, очередь, file_index targets, cached_bytes, количество нужных/завершённых pieces, last_played_at, текущая скорость, лимит, peers, последняя ошибка.

По умолчанию endpoints слушают loopback или защищаются аутентификацией. Webhook проверяет токен и быстро помещает событие в очередь обработки; получение metadata не должно блокировать подтверждение webhook.

Планируемая структура:
- исполняемый файл: `/opt/hotcached/`;
- конфигурация: `/etc/hotcached/`;
- состояние: `/var/lib/hotcached/`;
- кэш: `/mnt/hotcached/`;
- systemd: `hotcached.service`;
- отдельный пользователь `hotcached` с минимальными правами.

## 14. Ошибки и журналирование

Обрабатывать неверный webhook JSON, недоступность Jellyfin API, отсутствие MediaSource, чужой TorrServer, неверные hash/index, тайм-аут metadata, отсутствие peers, нехватку диска, ошибки SQLite/libtorrent и повреждённые resume data.

В журнал записывать тип события, ItemId (если доступен), infohash, file_index, очередь, действие и ошибку. Не записывать токены. Ошибки определения источника не должны влиять на воспроизведение.
