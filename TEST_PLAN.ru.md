# План тестирования и приёмки HotCached

[English](TEST_PLAN.md) | [Русская версия](TEST_PLAN.ru.md)

**Статус:** запланированные испытания. Наличие теста в этом документе не означает, что он уже пройден.

## Подход к тестированию

Используются три уровня:
1. **Модульные тесты** — разбор URL, определение источника, выбор pieces, учёт байтов, переходы очередей, вытеснение и проверка конфигурации.
2. **Компонентные тесты** — SQLite, metadata/piece behavior libtorrent, webhook и resolver Jellyfin API.
3. **Сквозные тесты** — webhook Jellyfin → HotCached → libtorrent → локальный peer TorrServer.

Для каждого интеграционного прогона фиксировать Ubuntu/kernel, версии Jellyfin и webhook plugin, версию/настройки TorrServer, версию libtorrent, public/private статус тестового torrent'а, piece length и сетевую топологию.

## A. Фильтрация источников

- [ ] Воспроизведение обычного локального MKV/MP4 не создаёт cache entry.
- [ ] STRM на другой host/port игнорируется.
- [ ] Совпадающий host, но неправильная служба/путь игнорируется.
- [ ] Валидный STRM на настроенный TorrServer принимается.
- [ ] STRM на SMB/сетевом ресурсе обрабатывается, если Jellyfin позволяет определить выбранный источник; место хранения не определяет принадлежность.
- [ ] При нескольких версиях/media sources решение принимается только по фактически выбранному источнику.
- [ ] Неизвестный или неоднозначный источник игнорируется и записывается в журнал.
- [ ] Неверный hash, URL, отрицательный/невалидный file index и неожиданный путь отклоняются.
- [ ] Query parameters и URL encoding не ломают разбор корректного URL.

## B. Поведение вебхуков

- [ ] ItemAdded для нашего источника добавляет PREWARM.
- [ ] PlaybackStart для нового источника добавляет ACTIVE.
- [ ] PlaybackStart для PREWARM переводит существующую запись в ACTIVE.
- [ ] PlaybackStart для ACTIVE обновляет last_played_at.
- [ ] Повторные/дублирующие вебхуки не создают дополнительные записи или handles.
- [ ] Повторный ItemAdded не обновляет возраст существующей записи.
- [ ] PlaybackProgress и PlaybackStop не меняют состояние кэша.
- [ ] Неверная аутентификация и повреждённый JSON отклоняются.
- [ ] Webhook быстро подтверждается, даже если получение metadata ещё продолжается.

## C. Выбор pieces

Проверять на контролируемых torrent metadata и файлах разных размеров, piece length и смещений файлов.

- [ ] Для большого однофайлового torrent выбираются только pieces, пересекающие первые 64 MiB и последние 16 MiB.
- [ ] У ненужных pieces priority 0, у нужных — priority 1.
- [ ] Piece, пересекающая границу диапазона, включается целиком.
- [ ] Файл меньше HEAD + TAIL даёт множество без дубликатов.
- [ ] Файл меньше HEAD покрывается диапазоном HEAD без неверных смещений.
- [ ] Файл ровно на границе диапазона обрабатывается правильно.
- [ ] Piece крупнее HEAD или TAIL всё равно включается целиком.
- [ ] Для multi-file torrent корректно сопоставляются диапазоны файла глобальным индексам pieces.
- [ ] Pieces, общие для двух media targets, учитываются один раз.
- [ ] Добавление второго target добавляет нужные pieces, не удаляя необходимые первому.
- [ ] Приоритеты применяются повторно после восстановления сессии.

## D. Учёт кэша и свободного места

- [ ] cached_bytes растёт только после полной загрузки и проверки нужной piece.
- [ ] Незавершённые pieces не учитываются.
- [ ] Общие pieces не учитываются дважды.
- [ ] После рестарта пересчёт даёт тот же объём проверенного payload.
- [ ] Видимый размер sparse-файла не используется как cached_bytes.
- [ ] До нарушения минимального резерва диска выполняется отказ или вытеснение.
- [ ] Запись, которая не помещается в байтовый бюджет очереди даже сама по себе, безопасно отклоняется.
- [ ] Вытеснение удаляет только файлы внутри настроенного каталога HotCached.

## E. Очереди и LRU

- [ ] Новый подходящий ItemAdded попадает в PREWARM.
- [ ] Новый подходящий PlaybackStart сразу попадает в ACTIVE.
- [ ] Promotion PREWARM → ACTIVE не создаёт второй handle и не теряет скачанные pieces.
- [ ] Повторный PlaybackStart обновляет актуальность ACTIVE.
- [ ] Повторный ItemAdded в PREWARM не обновляет added_at.
- [ ] Из ACTIVE вытесняется элемент с самым старым временем просмотра.
- [ ] Из PREWARM вытесняется самый старый по времени добавления.
- [ ] Независимо соблюдаются лимиты количества и байтов.
- [ ] Очередь может содержать меньше max_items, если это нужно для соблюдения byte budget.
- [ ] Освободившаяся полоса пустой очереди не передаётся другой.
- [ ] Изменение состава вызывает пересчёт лимитов всех torrent'ов затронутых очередей.
- [ ] Один torrent с несколькими file_index всё равно считается одним элементом очереди.

## F. Пропускная способность

- [ ] Один ACTIVE torrent получает лимит 15 Mbit/s; два — по 7.5 Mbit/s; N элементов делят бюджет 15 Mbit/s.
- [ ] PREWARM аналогично делит 5 Mbit/s.
- [ ] Session cap установлен на 20 Mbit/s.
- [ ] Преобразование Mbit/s в единицы libtorrent корректно.
- [ ] Фактическая скорость измеряется достаточно долго; мгновенные значения не трактуются как гарантированный лимит.
- [ ] Отдельно проверяются исключения local peers и upload limits.
- [ ] При одновременном трафике ACTIVE/PREWARM соблюдаются настроенные лимиты с допустимой погрешностью измерения/протокола.

## G. Metadata, peers и совместимость с TorrServer

- [ ] Metadata публичного тестового torrent можно получить только по infohash в поддерживаемых условиях.
- [ ] Тайм-аут metadata/отсутствие пиров ограничены по времени и отражаются в журнале.
- [ ] Результаты для private torrent'ов документированы; универсальная поддержка не заявляется без доказательств.
- [ ] HotCached и TorrServer подключаются к одному swarm одного infohash.
- [ ] TorrServer может получить piece, полностью загруженную и проверенную HotCached.
- [ ] Не закэшированная piece не объявляется доступной.
- [ ] Ограничения peers/upload не мешают TorrServer получать pieces.
- [ ] Передачу подтверждают по peer lists/logs TorrServer и состоянию peers libtorrent.
- [ ] На репрезентативных медиа сравниваются старт и поведение перемотки/чтения конца файла до и после прогрева.

Это обязательный release gate: **пока не доказана передача piece в TorrServer, основное предположение проекта не подтверждено.**

## H. Перезапуск и устойчивость

- [ ] После рестарта сохраняются очереди и last_played_at.
- [ ] Resume data восстанавливает валидные pieces и приоритеты.
- [ ] Отсутствующие/повреждённые resume data не обрушивают службу.
- [ ] Несовпадение состояния SQLite и файловой системы безопасно устраняется.
- [ ] Уменьшение лимитов конфигурации приводит к упорядоченному вытеснению при запуске.
- [ ] Временная недоступность Jellyfin/TorrServer не обрушает процесс.
- [ ] Ошибка libtorrent записывается и не повреждает другие записи очереди.

## I. Безопасность и эксплуатация

- [ ] API-токены не попадают в журналы и диагностические ответы.
- [ ] Аутентификация webhook обязательна.
- [ ] По умолчанию сервер слушает loopback.
- [ ] Служба работает от отдельного пользователя с минимальными правами.
- [ ] Процесс не может удалять или менять данные TorrServer.
- [ ] `/health`, `/status`, `/cache` возвращают полезную и ограниченную диагностику.
- [ ] Проверены перезапуск и завершение через systemd.

## Чек-лист релиза

- [ ] Модульные тесты пройдены.
- [ ] Интеграционные тесты пройдены на целевом компьютере.
- [ ] Реальный TorrServer получил проверенную закэшированную piece от HotCached.
- [ ] Проверены ACTIVE/PREWARM и общий лимит полосы.
- [ ] Проверены byte budget и восстановление после рестарта.
- [ ] README и дорожная карта отражают только подтверждённые результаты.
